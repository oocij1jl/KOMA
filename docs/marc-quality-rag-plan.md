# MARC 품질 / RAG 개선: 현행 분석 및 작업 순서

> **최신 수정 상태: [12장](#12-2026-10-01-653-분류-주제어와-245-부제-수집)을 기준으로 한다.** 정상 필드 과잉 삭제 수정은 11장, 브랜치 통합은 10장, 발표용 RAG 설명은 9장을 함께 참고한다.
> 1~10장은 각 작업 시점의 기록이다. 33권과 500권의 점수는 동일 표본의 전후 성능처럼 비교하지 않는다. 기존 재생성 결과와 이번 수정본의 새 생성 결과도 구분한다.

## 1. 이번 단계의 범위와 브랜치

이번 단계는 **코드 분석, 기존 결과 확인, 필드 분류, 개선 순서 설계, 기준선 고정**이다. 생성 로직·RAG·프런트 코드는 아직 변경하지 않았다.

브랜치는 추측이 아니라 실제 tree·log·diff 비교로 확정했다.

| 확인 | 명령 | 결과 |
|---|---|---|
| 커밋 동일성 | `git rev-parse origin/develop origin/feature/pipeline-v3` | 둘 다 `9e173e9`. 현재 작업 브랜치 HEAD도 같다 |
| 구현 규모 차이 | `git diff --stat origin/main..origin/develop` | 132개 파일, +26949 / -3 |
| 이력 구조 | `git log --all --graph --decorate --oneline` | `main`에는 초기 구조 2커밋만. 백엔드·RAG·평가는 모두 develop 계열 병합 |
| 중간발표 자료 | `git log -1 -- mid_result` | `27d89c3` `test: 중간발표회 도서 평가 데이터 추가 및 평가 지표 업데이트` |

- 분석·개선 기준: **`origin/develop` = `9e173e9`**. 같은 커밋인 `feature/pipeline-v3`를 따로 기준으로 잡을 이유는 없다.
- `main`은 초기 디렉터리·샘플만 있어 기준으로 쓸 수 없다.
- 작업 브랜치: **`feature/marc-quality-rag`**, `origin/develop`에서 생성 완료.
- 중간발표 자료 커밋 이후 develop에는 다건 처리·내보내기 등 변경이 더 있다.
- 따라서 **중간발표 저장 결과**와 **현재 코드로 새로 생성한 결과**를 같은 것으로 취급하지 않는다.
- 기존 `mid_result/`는 수정하지 않고 비교 기준으로 보존한다. 1단계 산출물은 이 브랜치에 로컬 커밋했고, 원격 push와 PR은 아직 하지 않았다.

브랜치 생성에 사용한 명령:

```sh
git switch -c feature/marc-quality-rag origin/develop
```

현재 이미 이 브랜치에 있으므로 다시 생성하지 않는다. 작업 커밋을 만든 뒤 원격에 처음 올릴 때는 아래처럼 대상 브랜치를 명시한다. 현재 upstream은 생성 기준인 `origin/develop`이므로 무심코 develop으로 push하지 않는다.

```sh
git push -u origin feature/marc-quality-rag
```

PR 대상은 `develop`으로 한다. 이번 작업에 관계없는 기존 변경을 함께 커밋하지 않는다.

## 2. 현재 코드 구조와 실제 생성 방식

### 2.1 백엔드 흐름

```text
ISBN
 → routers/generate.py
 → lookup_service.lookup_one
   → 국립중앙도서관 SearchApi
   → 정보나루 상세 / 키워드 / 이용분석 API
 → merge_biblio + merge_evidence
 → llm_input_builder.build_llm_input
 → marc_generator.build_prompt + rag_loader.load_rules
 → llm_client.generate
 → output_validator.validate_output
 → GenerateResult(fields, skipped_fields, warnings)
```

| 영역 | 주요 파일 | 분석 결과 |
|---|---|---|
| 외부 데이터 | `backend/clients/nl_client.py`, `data4library_client.py` | 서지값, 키워드, 책소개, 함께 대출된 도서 수집 |
| 병합·출처 | `backend/services/lookup_service.py:48-127` | 대체로 국중도 우선, 발행연도는 정보나루 우선. 선택된 일부 값에 `field_sources` 기록 |
| 추론 근거 | `backend/services/evidence_service.py` | keywords/description/co_loan_books/title/author/분류값/번역 정황 구성 |
| 생성 계약 | `backend/schemas/llm.py:19-64`, `llm_output.py` | 기본 생성 태그, 추론 근거 매핑, 결과 스키마 |
| 생성 | `backend/services/marc_generator.py:121-175` | **정형 필드까지 포함해 LLM이 전체 MARC JSON 생성** |
| 후처리 | `backend/services/output_validator.py` | JSON/스키마 확인, 650 제거, 무의미 값 제거, 653 오염어 필터 등 |
| 별도 검증 | `backend/routers/validate.py` | 주로 020/245/260 존재·필수 식별기호·ISBN 형식 검사. 완전한 KORMARC 규칙 검증 아님 |
| 교환파일 | `backend/routers/export.py` | pymarc를 통한 mrc/mrk/json. 제어필드·자료유형별 리더 정책은 별도 검토 필요 |
| 평가 | `ai/evaluation/evaluate_koma.py`, `evaluate_bulk.py` | 각각 gold 비교, 참조 정답 없는 대량처리 지표·수동검수 표 |

**중요: `source="api"`는 현재 “LLM 없이 생성했다”는 증거가 아니다.**

`marc_generator.py:170-175`는 LLM 결과를 후처리해 반환한다. `output_validator.py:87-100`은 태그가 020/245/260/700/710이면 `generated_by="api"`, 그 외에는 `"llm"`으로 사후 표기한다. 같은 파일 136-138행은 해당 태그에서 근거 없는 `ai_inference`를 `source="api"`로 바꾸기도 한다. 따라서 출처 라벨과 실제 생성 경로를 분리해서 개선해야 한다.

### 2.2 수집 가능한 값과 현재 수집하지 않는 값

- 국중도 매핑: ISBN·부가기호·세트 ISBN·가격·제목·저자·출판사·예정발행일·판사항·총서·권차·쪽수·크기·KDC·DDC 등.
- 정보나루 매핑: 제목·저자·출판사·발행연도·ISBN·분류번호·책소개, 별도 API의 키워드와 함께 대출된 도서.
- `pub_place`, `kdc_edition`, `ddc_edition`은 병합 코드에서 항상 빈 문자열이다 (`lookup_service.py:92,105,108`). **현 파이프라인만으로 발행지·분류표 판차를 확정할 수 없다.**
- 저자 정보는 역할별 구조화 배열이 아니라 문자열이다. 700/710 분리, 공저자·역자·그림작가 구분에는 추가 해석이 필요하다.
- API에 필드 매핑 코드가 있다는 사실과 각 도서에서 그 값이 실제 제공됐다는 사실은 다르다. 저장 결과만으로 당시 원본 API값을 복원할 수 없다.
- `biblio.subject`는 전달되지만 `field_evidence_map`의 주제어 근거로 명시되지 않는다. 이를 통제 주제명 대조 결과로 간주해서는 안 된다.

### 2.3 프런트·계약 조사 결과: 품질 개선의 연동 위험

다음은 정적 코드 분석이며 브라우저 재현은 이번 단계에서 하지 않았다.

- `frontend/src/api/marc.js`는 생성 API를 호출한다. 검증·백엔드 내보내기 API는 UI 경로에 연결되어 있지 않다.
- `MARCInput.jsx`는 생성 결과 배열을 콜백에 전달하지만 `HomeDashboard.jsx`는 단일 객체를 기대한다. **[INFERENCE] 검수 화면으로 결과 전달이 깨질 수 있다.**
- `MARCInput.jsx`의 API 오류 처리에 목업 결과 대체가 있다. 목업을 실제 생성 결과로 평가하면 안 된다.
- `MARCInspection.jsx`는 식별기호 단위 flat row로 편집하고, 저장 시 중첩 `fields/subfields` 형태를 보존하지 않는다. 부모에서 `onSave`도 전달하지 않는다.
- 프런트 TXT/JSON 다운로드는 백엔드 export와 별도 구현이다. 화면 출력과 ISO2709 내보내기의 품질을 같은 것으로 간주하지 않는다.
- `docs/api-spec.md`, `docs/marc-json-schema.md`, `shared/`는 초기 계약이 남아 있다. 현재 Pydantic 계약과 다르며, `backend/docs/KOMA_스키마_v2.1.md`에도 아직 구현되지 않은 prefix/display 등의 설계가 있다.

이 문제들은 별도 프런트 연동 작업으로 추적한다. **API/저장 JSON을 이용한 필드·RAG 개선 분석을 프런트 전체 개편이 끝날 때까지 미룰 필요는 없다.** 다만 최종 화면 시연·사서 검수까지 완료했다고 주장하려면 실제 화면 경로를 연결하고 확인해야 한다.

## 3. 현재 필드 목록과 세 가지 분류

### 3.1 집계 기준

`backend/schemas/llm.py:19-25` 기준:

- 기본 생성 시도 **17개**: 020, 041, 056, 082, 245, 246, 250, 260, 300, 490, 500, 546, 653, 700, 710, 830, 950.
- 별도 기본 제외 **1개**: 650. 규칙 파일은 있으나 기본 프롬프트 생성 태그에서 제외되고 후처리에서도 제거된다.
- 코드의 `required_fields`는 020/245/260/700/710이다. 이 명칭은 KORMARC 공식 필수성이나 실제 출력 보장과 같지 않다. 개인저자·단체저자를 무조건 둘 다 만들면 안 된다.
- 아래 생성 권수는 **중간발표 저장 JSON 33권에서 해당 태그가 있는 도서 수**다. 반복 필드 발생 횟수와 다르다. 예: 700은 23권에서 32회 발생한다.

분류는 **향후 책임을 어디에 둘 것인지(권장 분류)**를 나타낸다.

- **A — API 직접**: API의 명시된 서지값을 의미 추론 없이 채택. 형식 검사와 MARC 조립은 여전히 코드 책임.
- **B — 규칙 변환**: API 문자열을 식별기호로 분리하거나 날짜·단위·형식을 규칙으로 변환.
- **C — LLM 판단**: 비정형 문장의 역할·주제·주기 적합성 판단. 근거 없는 사실 생성은 금지.

**현재 실제 생성 경로는 태그와 무관하게 전부 LLM 1회 출력이다.** 세 범주 중 어느 것도 아직 코드로 분리돼 있지 않다.

| 구분 | 권장 분류 (이 문서의 A/B/C) | 현재 실제 경로 |
|---|---|---|
| 값을 만드는 주체 | 필드별로 코드 또는 LLM | 17개 태그 모두 LLM 1회 출력 |
| 코드의 역할 | 정형값 직접 생성, 규칙 변환, 형식 강제 | 생성 후 삭제·보정 중심 (`output_validator.py`) |
| `source="api"` 의미 | API 원본값을 코드가 채택함 | `020/245/260/700/710` 태그에 대한 **사후 라벨**. `output_validator.py:87-100`이 태그 집합만 보고 부여 |
| 근거 없는 추론 처리 | 생성 보류 | 위 태그면 `source="api"`로 승격되어 남는다 (`:136-138`) |

실측으로도 확인된다. 중간발표 저장 JSON 33권에는 `generated_by` 키 자체가 없고(`generated_by_labels=unset`), `source`는 태그 집합대로만 갈린다. 따라서 **지금의 `source="api"` 표기를 “API 직접 생성 완료”로 읽으면 안 된다.**

이 간극(정형·규칙 필드의 결정론 생성 레이어 부재)이 이번 개선의 최우선 항목이다. 아래 표의 권장 분류는 4단계에서 코드로 옮길 대상이다.

필드 하나에 여러 성격이 섞일 수 있으므로 권장 분류를 하나만 부여하고 예외를 명시한다. 특히 **API 값 부재를 자동으로 LLM 추론 허용으로 바꾸지 않는다.**

## 4. 기존 RAG의 상태와 보강 방법

### 4.1 실제 로딩 동작

- Markdown 원문: `ai/rag/docs/kormarc/fields/`.
- 런타임 입력: `ai/rag/chunks/kormarc-<tag>.jsonl`.
- `backend/services/rag_loader.py:28-85`는 태그별 파일을 통째로 읽어 프롬프트에 넣는다. 벡터 검색·유사도 순위 검색은 아니다.

### 5.3 평가기를 먼저 보완해야 하는 이유

- `evaluate_koma.py:63-71`: 245는 $a만, 260은 $b/$c만, 300은 $a/$c만 비교한다. 책임표시·발행지·삽화는 누락된다.
- `evaluate_koma.py:698-709`: 041 내용 비교는 $a 중심이다. 원어 $h의 정확도를 별도 측정해야 한다.
- `regularity_score`는 gold와 지시기호/식별기호 목록이 같은지 보는 점수다. **공식 KORMARC 적합성 점수 자체가 아니다.**
- `metric_row`는 gold에 없는 필드를 제외한다. 근거 없는 추가 041/082/500/546이 있어도 현재 점수만으로는 잡히지 않는다.
- 653은 gold의 650+653을 합쳐 비교하고, 부분일치도 accurate로 센다. 따라서 “정확도 74.19%”와 “주제어가 74.19% 정확하다”는 다른 말이다.
- gold 주제어에도 서명·저자 관련 문자열이 있고 서비스는 이를 제외하려 한다. 서비스 정책과 gold 문자열 일치를 혼동하지 말고 사서의 의미 적합성 판정을 함께 기록한다.
- `evaluate_bulk.py:207-229`는 필드 발생 횟수를 성공 도서 수로 나눈다. 반복 700 등이 여러 개이면 presence rate가 100%를 넘을 수 있다. 도서별 존재율과 필드 발생 횟수를 분리해야 한다.

기존 지표를 보존하면서 **개선된 평가기로 기존 결과와 신규 결과를 모두 다시 평가**한다. 평가 기준만 바뀐 상승을 생성 품질 향상으로 보고하지 않는다.

### 5.5 기준선 스냅샷 산출물

`ai/evaluation/baseline_snapshot.py`를 추가해 결과 디렉터리의 필드 현황을 고정했다. 이 스크립트는 결과 JSON과 gold만 읽고 원본을 수정하지 않으며, API·LLM도 호출하지 않는다.

기록에서 **확인 불가로 명시한 항목**(추정하지 않음):

- 중간발표 결과 생성 당시의 LLM 모델명과 호출 파라미터. 결과 JSON에 없다.
- 당시 API 조회 시점과 원본 응답. 저장돼 있지 않아 값 결측 여부를 사후 확인할 수 없다.
- 당시 `D4L_SKIP_USAGE` 설정값.

참고로 저장된 33권에는 `generated_by` 키가 아예 없다(`generated_by_labels=unset`). 현재 코드가 부여하는 `generated_by`는 중간발표 이후 추가된 것이므로, 전후 비교 시 이 필드의 유무를 품질 변화로 읽지 않는다.

**이 비교의 한계(반드시 감안할 것)**

- 입력이 실제 API 값이 아니라 저장된 생성 결과에서 역산한 값이다. 예를 들어 300은 저장값 `152 x 224`에 단위가 없어 크기가 빠졌고, 그래서 정확 2건이 0건이 됐다. 실제 API `book_size`는 `188*257mm`처럼 단위가 있어 위 스모크에서는 `26 cm`가 정상 생성됐다.

- 따라서 **값 정확도 개선 폭은 8단계 재생성 후에 확정해야 한다.** 지금 확정적으로 말할 수 있는 것은 구조 위반 29 → 0과 근거 없는 과잉 생성 감소다.

### 10단계 — 평가 기준 v2 수립과 재평가 (완료)

8단계 재생성은 2026-09-25 로컬에서 수행됐다(`eval_results/`). 이 결과를 `ai/evaluation/runs/after-rag/results`로 복사해 고정했고, 필드 현황은 `ai/evaluation/baseline/after-rag/`에 스냅샷으로 남겼다. 모델·`D4L_SKIP_USAGE`는 `backend/.env`에 지정이 없어 config 기본값으로 기록했다(셸 환경변수는 미확인).

**왜 v2가 필요한가.** 보강된 RAG의 핵심은 "근거가 없으면 만들지 않는다"이다. v1의 생성률·정확도로는 올바른 보류가 감점되고, 근거 없는 과잉 생성(출판사를 710에, 245와 같은 246)은 드러나지 않는다. v1은 기준선 재현을 위해 그대로 두고, `ai/evaluation/evaluate_v2.py`를 새로 만들었다.

| 축 | 무엇을 보나 | 분모 |
|---|---|---|
| A 값 정확도 | gold와 값 비교. 부분점수 평균과 exact 비율. 700 인명 F1 신설, 245 책임표시는 역할어를 토큰 단위로 제거, 653은 F1 | gold가 있는 (도서, 필드). 생성 안 했으면 0점 |
| B RAG 규칙 준수 | `ai/rag/chunks` generation/forbidden 규칙 18개를 코드 검사로 옮김 (245 구조, 발행지 추정, 300 단위, 830·950 금지, 546 무근거, 700=245 인원, 출판사 710, 중복 246, evidence 등) | 해당 필드가 있는 (도서, 규칙) |

### 9.2 이 프로젝트에서 RAG가 하는 일

**RAG는 모델이 외운 일반 MARC 지식 대신, 프로젝트가 준비한 KORMARC 필드 규칙을 참조하도록 돕는 장치다.** 책의 사실을 공급하는 API, 결정론적 변환 코드, LLM 출력 검증기와 역할이 다르다.

```text
ISBN
 └─ 국중도·정보나루 API 조회
     └─ biblio: 제목·저자·쪽수·분류 등 / evidence: 키워드·책소개·번역 정황
         ├─ 규칙 레이어: API 사실을 정해진 MARC 식별기호에 배치
         └─ LLM 대상 태그 선택
             └─ 태그별 JSONL 규칙 로딩 + biblio/evidence + 제약 + 출력 스키마
                 └─ LLM 생성
                     └─ 스키마·근거·생성 대상 검증
                         └─ 규칙 레이어 결과와 병합 → 사서 검수용 초안
```

역할 구분을 위한 도식이다. 실제 `generate_marc()`에서는 LLM 호출·검증 후 규칙 필드를 생성해 병합한다.

| 구성 | 실제 코드/자료 | 역할 |
|---|---|---|
| 규칙 원문 | `ai/rag/docs/kormarc/fields/*.md` | 사람이 검토하는 규칙·출처·서비스 정책 |
| 런타임 지식 | `ai/rag/chunks/kormarc-<tag>.jsonl` | LLM에 제공할 필드별 규칙 조각 |
| Retrieval | `backend/services/rag_loader.py:load_rules()` | 요청 태그에 해당하는 JSONL의 모든 유효 객체를 읽음 |
| Augmentation | `backend/services/marc_generator.py:build_prompt()` | 규칙, 서지 사실, 사용 가능 근거, 제약, JSON Schema를 프롬프트로 조립 |
| Generation | `backend/clients/llm_client.py` | 조립된 프롬프트로 모델 호출 |
| 규칙 생성 | `backend/services/deterministic_fields.py` | API 값 전사·정규화. RAG 문서를 실행하는 엔진은 아님 |
| 출력 검증·병합 | `output_validator.py`, `marc_generator.py` | 강제 가능한 정책 검사, 근거 없는 출력 제거, API 규칙값 보호 |

**현재는 태그 기반 규칙 검색형 RAG다.** 임베딩·벡터DB·유사도 top-k 검색·재순위화는 하지 않는다. `query_hints`가 있어도 검색 점수에 사용하지 않는다. 모델 파인튜닝도 아니다. Markdown을 수정하는 것만으로 런타임은 바뀌지 않으므로 JSONL도 함께 갱신해야 한다.

LLM 대상은 `700·653·041·246·500·546·710`이며 7개 모두 규칙이 로딩된다. `020·245·250·260·300·490·056·082`는 API 값에 규칙 코드를 적용하므로 LLM 대상에서 빠진다. 해당 규칙 문서·청크는 정책 기록으로 유지하지만 기본 LLM 프롬프트에는 넣지 않는다.

예를 들어 책소개에 **“영어 원작을 한국어로 번역”**이라고 명시돼 있으면:

1. API 책소개가 **사실 근거**다.
2. 041 규칙은 **본문언어는 `$a`, 원저작 언어는 `$h`**라고 설명한다.
3. LLM이 `$a kor`, `$h eng`을 제안한다.
4. 검증기가 실제 입력의 언어와 역할을 대조한다.

반대로 저자에 “옮김”만 있으면 번역 정황은 알 수 있지만 원어가 영어인지는 알 수 없다. RAG 규칙이 존재한다고 없는 원어 정보가 생기지는 않는다.

| 245 부제 16권 | 호출하는 API 출력 항목에 부제 필드가 없다 | 공식 출력 항목표 40개에 `TITLE(표제)`만 있고 부서명 항목이 없다. 같은 기관 ISBN/CIP 상세 페이지에는 `본표제 - 부제`가 있다 |
| 300 쪽수 | **기존 설명(“API=총 쪽수, gold=마지막 번호 쪽”)은 사실과 다르다.** 국중도 `PAGE`가 정답보다 작은 경우가 많다 | 33권 대조에서 불일치 21건 중 16건이 gold가 더 크다(`400>399`, `176>171`, `48>38`). 같은 33권을 교보 상품정보와 대조하면 **교보 쪽수가 23건, 국중도가 12건** 정답과 일치한다 |
| 056 분류 | **규칙·프롬프트로 고칠 수 없다** | `build_056`은 `biblio.kdc` 전사뿐이다. LLM도 규칙 판단도 개입하지 않으므로 `813.7`↔`813.8`, `185`↔`593.5` 불일치는 API 분류와 기관 목록자 판단의 차이다. 코드가 손댈 수 있는 부분은 API에 KDC가 없어 생성하지 못한 3권뿐이다 |
| 653 주제어 | 어휘 계통이 다르다 | gold는 `한국소설`·`아동문학`·`그림책` 같은 장르·독자 용어를 함께 쓰고, 기존 생성은 책소개에서 뽑은 소재어만 썼다 |

**이전 보고에서 056을 “주제 판단 개선 여지”로 분류한 것은 오류다.** 전사 경로에는 고칠 판단이 없다.

### 12.2 653 분류 주제어 (규칙 레이어)

`biblio.kdc`와 `biblio.isbn_add_code`가 이미 말하는 사실만 653으로 옮긴다. LLM 653과 근거가 다르므로 필드를 나눠 기술하고, 같은 주제어는 중복시키지 않는다.

- KDC 앞 두 자리가 문학류 언어권일 때만 적용한다(`81` 한국 … `88` 이탈리아). 그 밖의 분류는 만들지 않는다.
- 셋째 자리는 형식이며 `1` 시, `3` 소설, `4` 에세이만 쓴다.
- ISBN 부가기호 첫 자리가 `7`이면 `아동문학`(+`{언어권}동화`/`동시`), `4`면 `청소년문학`(+`청소년소설`), 그 밖이면 `{언어권}{형식}`을 더한다. 둘째 자리가 `7`(그림책)이고 아동 자료면 `그림책`을 더한다.
- `창작동화`·`역사동화`처럼 책을 읽어야 아는 구분은 분류기호에 없으므로 만들지 않는다. 이 용어를 넣으면 33권 F1은 30.2까지 오르지만 근거가 없어 채택하지 않았다.
- `source="api"`, `generated_by="rule"`, `review_required=true`로 두고 근거는 `note`에 분류기호·부가기호 원문으로 남긴다.
- LLM 653과 같은 오염 정책을 쓴다. 서명·부제·저자·출판사·총서명과 값이 완전히 같은 주제어는 제외한다.
- 요청이 653을 생성 대상에서 뺐으면(`generate_options.skipped_by_default`) 규칙 주제어도 만들지 않는다.
- 653 RAG 청크는 프롬프트에 그대로 들어가므로, 청크 첫 문장에 "이 경로는 규칙 레이어가 수행하고 LLM은 생성하지 않는다"를 명시했다.

### 12.3 245 부제·300 쪽수 수집 (3개 수집원)

부제 우선순위는 **알라딘 상품 API → 국중도 ISBN/CIP 상세 페이지 → 교보문고 상세**다. 공식 API를 먼저 쓰고, 화면 구조에 의존하는 경로를 뒤에 둔다. **쪽수는 교보를 먼저 쓴다**(위 12.1의 23:12 대조).

| 수집원 | 방식 | 확인한 사실 |
|---|---|---|
| 알라딘 | 상품 조회 API `ItemLookUp.aspx` (TTBKey 필요) | `subInfo.subTitle`(부제)·`originalTitle`(원제)·`itemPage`(쪽수)·`packing.sizeWidth/Height`(판형 mm)를 공식 제공한다 |
| 국립중앙도서관 | ISBN/CIP 상세 페이지 | ISBN 서지정보 API 출력 항목 40개에는 부제가 없다. 상세 페이지는 `본표제 - 부제` 형태로 보여주며 인증키가 필요 없다 |
| 교보문고 | 검색 → 상세 2단계 HTML | 공개 API가 없다. 상세 URL을 바로 열면 본문이 비고(크기 0), 검색 페이지로 세션 쿠키를 받고 Referer를 붙여야 HTML이 온다. `<h1 aria-label="본표제">` 다음 `<p aria-label="부제 \| 판형">`에서 부제를, `기본정보` 표의 `쪽수/크기`에서 `400쪽 \| 128 * 197 * 34 mm`를 얻는다 |

- 부제는 **표제사항이 API 본표제로 시작하고 뒤에 ` - ` 또는 ` : `가 올 때만** 떼어낸다. ` = `는 245 규칙상 대등표제(`$x`)이므로 부제 구분자로 쓰지 않는다.
- 떼어낸 뒤 다시 `:`나 `=`가 나오면 그 뒤는 책임표시·대등표제이므로 버린다(`처단 - 그날 계엄을 막지 못했더라면 :정보라 소설` → `$b 그날 계엄을 막지 못했더라면`).
- 표제 자체에 `:` 구분자가 있으면 기존 분리를 우선한다. 수집값은 `biblio.subtitle`에 담고 `field_sources.subtitle`에 출처(`aladin`/`nl_seoji_detail`/`kyobo`)를 남긴다.
- 쪽수는 `교보 → 국중도 → 알라딘` 순이다. 크기는 `국중도 → 교보 → 알라딘` 순으로 둔다. 교보 크기값은 `가로 * 세로 * 두께 / 무게` 형식이라 가로·세로만 취하고 두께·무게는 버린다.
- 교보는 쪽수까지 쓰므로 책마다 항상 호출한다(검색 1회 + 상세 1회). 알라딘 키가 없으면 알라딘은 호출하지 않는다. 어느 수집원이 실패해도 조회 전체는 계속된다.

#### 검토했으나 쓰지 않은 수집원

- **카카오 디벨로퍼스 Daum 책 검색**(`GET https://dapi.kakao.com/v3/search/book`, REST API 키). 응답 필드는 `title, contents, url, isbn, datetime, authors, publisher, translators, price, sale_price, thumbnail, status`다. **부제·쪽수·판형·원제가 모두 없어** 알라딘을 대체하지 못한다. 유일한 추가 정보는 구조화된 `translators`(번역자 목록)이며, 041/546 번역 근거로는 쓸 수 있으나 지금 격차와 무관해 붙이지 않았다.
- **네이버 검색 API 책**(`GET https://openapi.naver.com/v1/search/book`, Client ID/Secret). 응답 필드는 `title, link, image, author, discount, publisher, isbn, description, pubdate`다. **쪽수·판형·원제가 없고 부제 전용 필드도 없다.** 부제는 `불곰의 주식투자 불패공식 (60개 매도종목 평균 수익률 62%)`처럼 제목 끝 괄호에 섞여 오므로, 괄호가 부제인지 판형·권차 표시인지 구분할 근거가 없다. 이미 국중도·교보에서 분리된 부제를 받고 있어 추가 이득이 없다고 보고 붙이지 않았다.

### 12.5 실제 조회로 확인한 한계

- 부제는 **재현율 15/16, 정밀도 15/22**다. gold에 부제가 있는 16권 중 15권을 맞혔고, gold가 부제를 적지 않은 6권에 `$b`가 새로 생겼다. 평가 A에서는 감점되지 않지만 기관이 쓰지 않는 선전 문구일 수 있으므로 `review_required=true`와 note로 검수에 넘긴다.
- 1권(`9791199605336`)은 화면이 `사라지는 동물을 살리는`, gold가 `지키는`이다. **출판사 등록값과 목록자 기술이 다른 사례이며 코드로 해결할 수 없다.**
- 교보 쪽수도 완전하지 않다. 그림책의 `[33] p.`·`[80] p.`처럼 번호 없는 쪽을 각괄호로 세는 목록 규칙은 실물을 봐야 한다. 300 exact가 57.6에서 멈추는 이유다.
- 알라딘 경로는 **인증키가 없어 실제 호출로 검증하지 못했다.** 응답 정규화·오류 처리는 MockTransport 단위 테스트로만 확인했다. 키를 넣고 한 번 실제 호출로 확인해야 한다.
- 교보 경로는 공식 API가 아니며 세션 쿠키·화면 구조에 의존한다. 구조가 바뀌면 부제·쪽수만 비고 나머지 필드는 영향받지 않는다. 책당 요청이 2회 늘어난다.
- 653 분류 주제어는 **분류기호가 틀리면 같이 틀린다.** 아동 도서 8권은 API KDC가 `813.7`(일반 소설)이어서, 아동 판정은 ISBN 부가기호에 의존한다. gold 주제어 대부분은 `오징어땅콩`·`민금봉`처럼 책마다 다른 고유명사라, 이 경로의 653 F1은 30 부근에서 포화한다.
- 측정은 33권 표본이다. 500권 표본의 값은 이 수치로 대체할 수 없다.
